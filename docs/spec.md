# Market Pulse — техническое задание (v1)

Статус: черновик. Все числовые пороги — стартовая гипотеза, а не истина.
Они будут проверяться позже через SQL-анализ накопленных прогонов.

---

## 1. Проблема

При ручном анализе рынка трейдер открывает список из сотен инструментов и
листает графики, пытаясь понять, где вообще есть жизнь. Большинство
инструментов неликвидны или неактивны. Основное время уходит не на анализ,
а на **поиск того, что достойно анализа**.

## 2. Что делает система

1. Получает список торгуемых инструментов с бирж.
2. Отсеивает заведомо неподходящие (низкая ликвидность, короткая история).
3. Считает метрики активности по каждому оставшемуся.
4. Ранжирует и оставляет топ-N.
5. Для каждого кандидата формирует **человекочитаемое объяснение**.
6. Сохраняет прогон в базу для последующего исследования.

Система **не** говорит «покупай». Она говорит: **«из 400 инструментов вот эти
15 ведут себя необычно — посмотри их сам»**.

---

## 3. Источники данных

| Биржа | Рынок | Что берём |
|---|---|---|
| Binance | USDⓈ-M Futures | список символов, 24h тикер, свечи 15m |
| OKX | Perpetual Swaps (USDT) | то же |

Только публичные REST-эндпоинты. Ключи API не используются.
Учитывать rate limits: запросы свечей идут пачками с паузами.

---

## 4. Базовые соглашения

Эти определения фиксируются один раз и используются везде:

- **Таймфрейм анализа:** **15 минут** (основной). 5 минут — альтернативный
  режим, переключается параметром в конфиге.
- **Текущая свеча:** последняя **полностью закрытая** свеча.
  Обозначается `t`. Незакрытая свеча в расчётах **не участвует** —
  иначе метрика зависит от того, в какую минуту запущена программа.
- **Базовое окно (baseline):** **ровно 48 часов** — с `t-N` по `t-1`
  включительно. Текущая свеча в окно **не входит**.

  | Таймфрейм | N свечей | Окно |
  |---|---|---|
  | 15m | 192 | 48 ч |
  | 5m  | 576 | 48 ч |

  **Почему окно задаётся в часах, а не в свечах.** У рынка есть суточный
  цикл: азиатская, европейская и американская сессии дают разный «обычный»
  объём. Если окно не кратно суткам (например, 42 часа), одни часы суток
  попадают в базу дважды, другие — один раз, и медиана оказывается смещена
  к переизбыточной сессии. Инструмент тогда выглядит аномальным просто
  потому, что сейчас активная сессия. Окно, кратное 24 часам, эту ошибку
  убирает. При смене таймфрейма меняется число свечей, но **не длина окна**.
- **Тип усреднения:** **медиана**, не среднее арифметическое.
  Причина: один памп внутри недели задирает среднее и делает метрику слепой.
  Медиана показывает «обычное состояние инструмента».
- **Объём:** считается в **quote-валюте (USDT)**, не в монетах.
  Иначе инструменты с разной ценой несравнимы между собой.

## 5. Фильтры (до расчёта метрик)

Инструмент отбрасывается, если выполняется любое условие:

| Фильтр | Порог | Зачем |
|---|---|---|
| Статус торгов | не активен | делистинг, пауза |
| Котируемая валюта | не USDT | сопоставимость |
| Оборот за 24ч | < 5 000 000 USDT | отсев неликвида |
| Длина истории | < (N + 1) свечей | baseline неполный, метрика недостоверна |
| Число сделок за 24ч | < 10 000 | «мёртвый» инструмент |

`N` — размер базового окна из раздела 4 (192 для 15m, 576 для 5m).
Отдельного фильтра «сколько дней с листинга» нет: требование полной истории
окна автоматически отсекает только что вышедшие инструменты.

Результат этапа логируется: сколько было всего, сколько отсеял каждый фильтр.
Это само по себе полезная информация.

## 6. Метрики

### 6.1 RVOL — относительный объём

```
V_t       = объём (в USDT) текущей закрытой свечи
V_median  = медиана объёмов свечей [t-N … t-1]
RVOL      = V_t / V_median
```

Смысл: во сколько раз объём последней свечи отличается от обычной свечи
этого инструмента за последние двое суток.

Порог интереса: **RVOL ≥ 3.0**

### 6.2 RTC — относительное число сделок

```
N_t       = количество сделок в текущей закрытой свече
N_median  = медиана количества сделок [t-N … t-1]
RTC       = N_t / N_median
```

Смысл: RVOL и RTC намеренно разделены. Если объём вырос, а число сделок нет —
работали крупные участники. Если выросло число сделок — пришла толпа.
Это разные ситуации, и объяснение должно их различать.

Порог интереса: **RTC ≥ 2.5**

### 6.3 VE — расширение волатильности

Через True Range (стандартная формула):

```
TR_i      = max( High_i − Low_i,
                 |High_i − Close_(i−1)|,
                 |Low_i  − Close_(i−1)| )

TR_norm_i = TR_i / Close_i        # нормировка, чтобы сравнивать разные цены

TR_median = медиана TR_norm по [t-N … t-1]
VE        = TR_norm_t / TR_median
```

Смысл: диапазон последней свечи относительно её обычного диапазона.
Порог интереса: **VE ≥ 2.0**

### 6.4 Направление (справочно, не влияет на score)

```
CHG = (Close_t − Close_(t-1)) / Close_(t-1) × 100%
```

Показывается в отчёте, чтобы было видно, движение вверх или вниз.
На ранжирование **не влияет** — система не предсказывает направление.

### 6.5 ATS — изменение среднего размера сделки (справочно, не влияет на score)

RVOL и RTC вместе уже содержат ответ на вопрос «крупные участники или толпа
мелких». Считать ничего нового не нужно — величина получается делением:

```
        RVOL     V_t / V_median        V_t / N_t
ATS  =  ────  =  ──────────────  =  ─────────────────
        RTC      N_t / N_median      V_median / N_median
```

Числитель `V_t / N_t` — средний размер сделки в анализируемой свече.
Знаменатель `V_median / N_median` — обычный средний размер сделки.

**Важная оговорка о точности.** Знаменатель — это отношение медиан, а не
медиана отношений. Эти две величины в общем случае не равны. Отношение медиан
выбрано потому, что оно получается из уже посчитанных RVOL и RTC тождественно,
без обращения к свечам; медиана отношений потребовала бы отдельного прохода
и дала бы величину, не связанную с RVOL и RTC простой формулой.

Смысл:

| ATS | Что произошло |
|---|---|
| заметно больше 1 | объём принесли более крупные сделки, чем обычно |
| около 1 | сделок стало больше, а их размер прежний |
| заметно меньше 1 | пришло много мелких сделок |

На score **не влияет** и в отбор кандидатов не входит. Используется только
в тексте объяснения (раздел 8) — ради того различия, ради которого RVOL и RTC
и разведены в отдельные метрики.

## 7. Скоринг

Каждая метрика нормируется относительно своего порога и ограничивается
сверху, чтобы один экстремальный выброс не перекрывал всё остальное:

```
s_rvol = min( RVOL / 3.0, 3.0 )
s_rtc  = min( RTC  / 2.5, 3.0 )
s_ve   = min( VE   / 2.0, 3.0 )

SCORE  = 0.4 × s_rvol + 0.3 × s_rtc + 0.3 × s_ve
```

Инструмент попадает в кандидаты, если **хотя бы две** метрики из трёх
превысили свой порог (защита от разовых аномалий в одном показателе).

Веса `0.4 / 0.3 / 0.3` — **гипотеза первой версии**. Они специально вынесены
в конфиг, чтобы позже проверить их SQL-запросами по накопленным данным.

Выводится топ **15 кандидатов по каждой бирже отдельно** (то есть до 30 всего).
Списки не объединяются и не дедуплицируются: один и тот же актив может попасть
в оба списка, и это нормально — сравнение его поведения на разных биржах само
по себе информативно.

**Замечание про короткий таймфрейм.** На 15m и особенно на 5m метрики шумнее,
чем на часовом: всплеск в 3× случается чаще и реже означает что-то значимое.
Ожидаемо будет больше ложных срабатываний. Это не повод менять пороги заранее —
именно этот вопрос и должна закрыть таблица `outcomes` (раздел 9) на реальных
данных.

## 8. Формат вывода

```
Market Pulse — свеча 15m, закрытие 2026-08-12 14:15 UTC
База сравнения: 192 свечи (48 ч), медиана

BINANCE   проверено 412 → после фильтров 287 → кандидатов 15
────────────────────────────────────────────
 1. SUI/USDT                    score 2.31
────────────────────────────────────────────
    Изменение за свечу:  +4.2 %

    Почему в списке:
    • Объём свечи 8.4M USDT — в 4.1× выше обычного
      (обычная свеча 15m за 48 ч: 2.0M USDT, медиана)
    • Сделок 31 400 — в 2.9× больше обычного
      (обычно 10 800 за свечу)
    • Диапазон свечи 3.8 % — в 2.4× шире обычного
      (обычно 1.6 %)

    Итог: выросли одновременно объём, число сделок и волатильность —
    инструмент вышел из своего обычного режима.
```

Ключевое требование: пользователь должен видеть **и коэффициент, и абсолютные
числа, на основании которых он получен**. Голый «score 2.31» неприемлем.

## 9. Схема базы данных (SQLite)

```sql
-- один запуск программы
CREATE TABLE runs (
    id          INTEGER PRIMARY KEY,
    started_at  TEXT NOT NULL,      -- UTC ISO8601
    candle_time TEXT NOT NULL,      -- время открытия анализируемой свечи
    total_symbols     INTEGER,      -- всего перпетуалов USDT на бирже
    passed_filters    INTEGER,      -- прошло фильтры ликвидности
    analysed_symbols  INTEGER,      -- осталось после отсева короткой истории
    candidates_count  INTEGER,      -- прошло правило «2 метрики из 3»
    config_json TEXT                -- пороги и веса этого прогона
);

-- инструменты, попавшие в кандидаты
CREATE TABLE candidates (
    id        INTEGER PRIMARY KEY,
    run_id    INTEGER NOT NULL REFERENCES runs(id),
    exchange  TEXT NOT NULL,
    symbol    TEXT NOT NULL,
    rank      INTEGER NOT NULL,
    score     REAL NOT NULL,
    rvol      REAL, rtc REAL, ve REAL,
    price     REAL, change_pct REAL,
    volume_usdt REAL, trades INTEGER,
    quote_volume_24h REAL           -- оборот инструмента за 24 ч на момент прогона
);

-- что было с ценой ПОСЛЕ попадания в список
CREATE TABLE outcomes (
    candidate_id INTEGER PRIMARY KEY REFERENCES candidates(id),
    ret_30m  REAL,          -- % изменения через 30 минут
    ret_2h   REAL,
    ret_8h   REAL,
    max_move_2h REAL,       -- максимальное отклонение в любую сторону за 2 ч
    filled_at TEXT
);
```

Два поля добавлены к первоначальной схеме:

- `candidates.quote_volume_24h` — без него нельзя проверить, отличается ли доля
  отработавших кандидатов у инструментов разной ликвидности, а порог оборота
  как раз является гипотезой. Восстановить это поле задним числом невозможно:
  оборот за 24 ч меняется каждую секунду.
- `runs.analysed_symbols` — воронка состоит из четырёх чисел, а не из трёх:
  между фильтрами и кандидатами есть отсев по неполной истории.

`candidates_count` — сколько инструментов прошло правило «две метрики из трёх».
Строк в таблице при этом не больше `top_n`: список кандидатов усечён. Разница
между этими числами сама по себе информативна и восстанавливается запросом.

Таблица `outcomes` — самая важная для карьерной части проекта. Она превращает
инструмент в **исследование**: позволяет SQL-запросами проверять,

- при каких значениях RVOL/RTC/VE чаще случались сильные движения;
- какие пороги дают много ложных срабатываний;
- отличается ли поведение кандидатов на Binance и OKX;
- какие веса в скоринге работают лучше.

Именно это стоит показывать работодателю, а не только «я умею дёргать API».

## 10. Этапы разработки

Каждый этап — законченный и проверяемый результат.

| # | Этап | Результат |
|---|---|---|
| 1 | Клиент Binance: список символов + 24h тикер | в консоли список инструментов с оборотом |
| 2 | Фильтры | видно, сколько отсеялось и по какой причине |
| 3 | Загрузка свечей 15m для прошедших фильтр | данные лежат в памяти/кэше |
| 4 | Расчёт RVOL, RTC, VE | таблица метрик по инструментам |
| 5 | Скоринг и отбор топ-15 | ранжированный список |
| 6 | Отчёт с объяснениями | вывод как в разделе 8 |
| 7 | SQLite: сохранение прогонов | база наполняется |
| 8 | Подключение OKX | вторая биржа в общем списке |
| 9 | Сбор outcomes | появляются данные для анализа |
| 10 | SQL-исследование + README | выводы, графики, готовое портфолио |

Этапы 1–6 дают уже полезный работающий инструмент.
Этапы 7–10 превращают его в проект для резюме.

## 11. Зафиксированные решения

| Вопрос | Решение | Почему |
|---|---|---|
| Таймфрейм | 15m основной, 5m опцией | ближе к скальпингу; 5m шумнее, оставлен переключателем |
| Базовое окно | 48 часов (192 или 576 свечей) | кратно суткам — убирает перекос по сессиям |
| Тип усреднения | медиана | устойчива к разовым пампам внутри окна |
| Размер выдачи | топ-15 на каждую биржу | комфортно для ручного просмотра |
| Дедупликация между биржами | нет | одинаковый актив на двух биржах — полезное наблюдение |
| Фильтр по дате листинга | нет отдельного | покрывается требованием полной истории окна |

Всё остальное (пороги, веса) — параметры конфига, проверяются по данным.
